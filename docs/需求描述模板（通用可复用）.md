# 项目需求描述模板（可直接提交给 AI 大模型构建）

> 用途：在**另一台电脑**上从零构建一个**用途不同但完善程度相当**的完整项目时，把本模板的占位符填好，整段复制给任意 AI（Claude / GPT / 通义 / 本地大模型等），即可无歧义地传达构建要求。
> 设计原则：本模板本身就是针对"项目做出来却是空壳 / 不可移植 / 缺文档"等典型失败而写的。**所有【】内为你需要填写的内容。**

---

## 0. 一句话交付要求（给 AI 的硬指标）

请构建一个**自包含、可独立运行、功能真实可用（非演示壳）**的完整项目，而不是原型 demo。交付物必须能在一台只装了【Node/Python/……】的干净机器上，按 README 步骤跑起来，且**每个声明的功能都经你实际验证可用**。

---

## 1. 项目目标（必须明确"为什么存在"）

- 项目名称：【例如：本地读书笔记管理器】
- 一句话定位：【例如：把本地 PDF/EPUB 读书笔记统一归档、检索、导出】
- 目标用户：【例如：个人研究者 / 小团队】
- 解决的核心痛点：【例如：笔记散落在多个 App、无法全文检索、导出格式乱】
- 成功标准（可量化）：【例如：导入 100 篇文档 < 30s；全文检索命中率 > 95%】

> 写不清目标，AI 就会自作主张加一堆你不要的功能。这条必须写。

---

## 2. 功能范围（用 MUST / SHOULD / WON'T 三档，杜绝"做了个空架子"）

### MUST（必须有，且必须真能跑通，不只是页面渲染）
1. 【功能 A】：【例如：上传 PDF/EPUB，解析出正文与目录】——验收：真实文件上传后返回解析结果，不是假进度条。
2. 【功能 B】：【例如：全文检索，按相关度排序】——验收：搜一个词能返回真实命中片段。
3. 【功能 C】：【例如：笔记导出为 Markdown/HTML】——验收：导出文件真实可读。
4. ……

### SHOULD（有则更好，时间不够可后做，但要做就做完整）
1. 【功能 D】：【例如：标签体系】
2. ……

### WON'T（明确不做，防止范围蔓延）
1. 【例如：不做云端同步、不做多用户协作、不做移动端】
2. ……

> 关键约束：**MUST 里的每一项，AI 交付时必须附"真实验证证据"（返回数据样本 / 截图 / HTTP 状态 / 点击录屏）。只把服务拉起来返回 200，不算功能可用。**

---

## 3. 技术栈与运行环境（必须明确，避免"我机器上有就能跑"）

- 语言/运行时：【例如：Node.js 20+ / Python 3.11+】，版本写死范围，但**不要写死某台机器的绝对 exe 路径**。
- 核心框架：【例如：Express + 原生前端 / FastAPI + React / 零依赖单 HTML】
- 依赖管理：【必须 `package.json` / `requirements.txt` + `npm install` / `pip install -r` 可装，禁止"手动配 NODE_PATH 或依赖机器上某个目录"】
- 数据存储：【例如：SQLite 文件 / JSON 文件 / 内存】，初始数据如何生成写清楚。
- 外部 API/密钥：【例如：如需调用某 API，用 `.env` + 提供 `.env.example`，密钥不得写死在代码里】

---

## 4. 目录结构与模块边界（明确约定，避免上帝文件与隐性耦合）

建议结构（按你项目调整）：

```
【项目名】/
├── README.md            # 必含：简介/技术栈/环境/安装/启动/结构/配置/FAQ
├── package.json         # 必含 dependencies + scripts.start
├── .env.example         # 配置样例（不含真实密钥）
├── src/                 # 后端/核心逻辑
│   ├── server.js        # 入口
│   └── modules/         # 每个功能一个模块，独立自洽
├── public/ 或 assets/   # 前端（若前端由本项目提供，必须在此，且能被服务正确托管）
├── data/                # 运行时数据（明确持久化方式）
└── tests/ 或 验收脚本    # 端到端验证脚本
```

模块边界硬规则：
- **每个功能模块必须自洽**：自己提供后端 API，并且（若需要 UI）自己提供能被服务托管的前端资产。禁止"前端渲染一个空容器，然后隐性依赖另一个服务恰好在某个端口提供资产却没提供"的耦合。
- 前端若依赖全局对象（如 `window.xxxManager`），**必须显式挂载并验证其存在**后再 init；脚本加载加版本/cache-bust 避免缓存旧脚本。
- 跨文件/跨模块引用一律用相对路径或 `path.join(__dirname, …)` / `import.meta.url`，**严禁 `require('D:/其他项目/...')` 这类绝对跨项目引用**。
- 复用别人代码的正确方式：抽成 npm 包 / git submodule / 复制进本项目并注明来源——而不是运行时去另一个项目目录里读文件。

---

## 5. 配置与数据约定

- 所有可变配置集中在【config.json / .env】，不散落硬编码。
- 配置项清单：【列出每个配置项的含义、默认值、是否必填】
- 数据持久化：【文件 / SQLite / 内存】，位置、格式、初始种子数据如何生成。
- 首次启动行为：【例如：自动建库、无数据时不崩、给出空状态 UI】

---

## 6. 约束条件（硬性，踩过的坑都写在这里）

1. **自包含 / 可移植**：在一台干净机器上 `clone → 装依赖 → 启动` 必须成功。任何"需要机器上恰好有某个外部项目/目录"的依赖都禁止。
2. **禁止硬编码绝对路径**：尤其是其他项目的路径、用户主目录（如 `C:/Users/xxx`）、特定 node 路径。路径必须可配置或通过环境变量解析。
3. **端口/资源自托管**：本项目需要的任何前端资产（JS/CSS），必须由本项目自身服务提供（如 `express.static('public')`），不得依赖外部端口恰好存在。
4. **真实可用验收**：见第 2 节。端口 health 200 ≠ 功能可用。
5. **工作区整洁**：交付物中**不得**残留 `_scratch.cjs`、`*.bak`、调试日志、设计截图等临时文件。
6. 【你项目的其他硬约束，例如：必须离线可用 / 必须中文界面 / 必须零外部网络调用】

---

## 7. 验收标准 / Definition of Done（AI 交付前逐项自检）

AI 在宣布"完成"前，必须逐条确认并给出证据：

- [ ] `npm install`（或等价）成功，无遗漏依赖
- [ ] 启动命令一次跑通，无手动改路径/改环境变量
- [ ] 每个 MUST 功能都有**端到端真实验证证据**（不是仅页面渲染、不是仅端口 200）
- [ ] 前端交互（点击/输入/提交）真实触发后端行为，有反馈
- [ ] 无硬编码绝对路径；换目录/换机器仍可运行
- [ ] 无跨项目绝对引用；所有依赖在项目内或经包管理安装
- [ ] 配置文件齐全，`.env.example` 提供，密钥未写死
- [ ] README 完整覆盖：安装 / 启动 / 结构 / 配置 / 常见问题
- [ ] 工作区无临时/调试/备份垃圾文件
- [ ] 【你项目的专属验收项】

---

## 8. 协作与交付节奏（可选，但强烈建议写上）

- **先方案后实现（report-first）**：AI 先输出"范围 + 技术选型对比 + 分阶段路线 + 风险"的结构化方案，经你确认再动手。
- **每轮回执**：做完后说明"产出哪些文件 / 怎么打开 / 做了哪些验证 / 还有哪些未决项"。
- **不做超出范围的动作**：未经确认不擅自加功能、不擅自建文件、不清你没确认的文件。

---

## 9. 反模式黑名单（给 AI 的明确"不要这样做"）

- ❌ 不要只把服务拉起来返回 200 就声称"功能可用"
- ❌ 不要渲染一个空 div 然后依赖一个没提供的外部资产
- ❌ 不要 `require('D:/某项目/...')` 跨项目绝对引用
- ❌ 不要把 Node/Python 路径、用户目录写死在配置文件里
- ❌ 不要留一堆 `_调试.cjs`、`*.bak`、日志在交付目录
- ❌ 不要没有 README 就交付
- ❌ 不要在前端用 `const x = ...` 却指望它自动变成 `window.x`（经典"初始化没跑"坑）

---

> 使用方式：把以上【】填好，整段发给 AI 即可。若项目较大，可把第 2 节（功能范围）按模块拆成多个需求分别提交，但务必保留第 6、7、9 节的硬约束。
